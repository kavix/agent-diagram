# LLM Cost Efficiency Guide: `agent-diagram`

> How to get maximum diagram accuracy at minimum token cost.

---

## The Token Economics of `render_diagram`

Every time an LLM calls `render_diagram`, tokens are spent in two places:

| Cost Point | Tokens (approx) | Controllable? |
|:---|:---|:---|
| Tool schema in system context (`tools/list`) | 80–120 | ✅ Tightened in v0.1.1 |
| Mermaid `source` argument generated by LLM | 50–400 | ✅ Use compact syntax |
| LLM response from tool call | 10–2000 | ✅ Use `response=summary` |
| Re-attempts after parse errors | 100–800 × N retries | ✅ Use `validate_diagram` first |

**Total per interaction (optimised):** ~150 tokens  
**Total per interaction (unoptimised):** ~2500 tokens  
**Savings ratio:** up to **16×**

---

## 1. Always Use `response=summary` (Default)

The diagram is displayed directly on the user's terminal via stdout. **The LLM does not need to re-read it.** Summary mode returns ~10 tokens instead of the full render.

```json
{
  "name": "render_diagram",
  "arguments": {
    "source": "sequenceDiagram\n  A->>B: Hello",
    "response": "summary"
  }
}
```

**Response:** `✓ Rendered sequence diagram (3 events, 8 lines). Shown in terminal.`  
**Token cost:** ~12 tokens ✅

Compare to `response=full`:  
**Response:** `[full 40-line Unicode art]`  
**Token cost:** ~600 tokens ❌

---

## 2. Pre-Validate with `validate_diagram` Before Generating Complex Diagrams

For diagrams with more than 5 participants or 10 messages, use `validate_diagram` as a pre-flight check. It runs an O(n) scan with **zero render cost** and returns structured fix hints:

```json
{
  "name": "validate_diagram",
  "arguments": {
    "source": "sequenceDiagram\n  A B: no arrow"
  }
}
```

**Response:**
```
✗ Validation failed (1 error):
  1. [MISSING_ARROW] line 2: arrow found but no message label
     Fix: sequence messages need an arrow: use A->>B: message or A-->B: message
```

This saves a full render round-trip (the most expensive failure mode — the LLM generates 300 tokens of Mermaid, it fails, the error comes back, the LLM tries again).

---

## 3. Write Token-Efficient Mermaid Source

Every byte in the `source` argument is a token. Use short participant IDs with aliases:

```
# ❌ Expensive — participant IDs are used everywhere in message lines
sequenceDiagram
  participant OrchestrationAgent as Orchestration Agent
  participant WorkerAgentOne as Worker Agent One
  OrchestrationAgent->>WorkerAgentOne: message

# ✅ Cheap — short IDs, human-readable labels only in header
sequenceDiagram
  participant O as Orchestrator
  participant W1 as Worker 1
  O->>W1: message
```

Token savings: ~40% reduction in source tokens for 6-participant diagrams.

### Arrow Shorthand Priority (fewest tokens → most tokens)

| Arrow | Tokens | Use for |
|:---|:---|:---|
| `->>` | 3 | Default call (solid arrow) |
| `-->>`| 4 | Return / response |
| `-->` | 3 | Dotted (async, no arrowhead) |
| `-x`  | 2 | Rejected / blocked message |
| `--x` | 3 | Async rejected |

---

## 4. Obey the Participant Cap: ≤6 Per Diagram

Diagrams with more than 6 participants will:
- Exceed typical terminal widths (→ force compact mode → no 2D layout)
- Generate wider `source` strings (more tokens)
- The validator will warn at >8 participants

**Instead:** Split into two diagrams. The LLM calls `render_diagram` twice with smaller, clearer diagrams. Each costs fewer tokens and renders better.

```
# Split a 9-participant orchestrator diagram into:
# Diagram 1: User → Guardrail → Orchestrator → [3 workers]
# Diagram 2: Orchestrator → [3 remaining workers] → Synthesiser → User
```

---

## 5. Use `mode=compact` for Agent Tool Calls

The `auto` mode will pick full or compact based on terminal width. For agent tool calls where the LLM is not viewing a real terminal (e.g. CI, test harnesses), force `compact`:

```json
{ "mode": "compact", "width": 80 }
```

Compact mode renders in ~30% fewer characters than full mode, and the LLM can parse it more easily in `full` response mode if needed.

## 6. System Prompt / AGENTS.md Steering Rule (Minimal Tokens)

The AGENTS.md rule installed by `agent-diagram install-plugin` is already optimised. A verbose rule wastes tokens on every system prompt:

```markdown
# ❌ Verbose (47 tokens per system-prompt injection)
Whenever you are explaining architecture, distributed calls, Kubernetes
reconcilers, or workflows, always call the render_diagram tool with valid
Mermaid syntax (sequenceDiagram or flowchart TD/LR).

# ✅ Terse (19 tokens — same behaviour)
For architecture/flow explanations: call render_diagram with Mermaid syntax.
```

## 7. Error Recovery Pattern (Single-Shot Self-Correction)

When `render_diagram` returns a validation error, the response includes a machine-readable fix hint. The LLM should fix and retry **in the same turn** without asking the user:

```
Tool call:   render_diagram { source: "sequenceDiagram\nA B: bad" }
Tool result: ✗ [MISSING_ARROW] line 2 — Fix: use A->>B: message

LLM action:  render_diagram { source: "sequenceDiagram\nA->>B: bad" }  ← fixed
```

This is one tool call instead of two (no round-trip to the user). Structured error codes (`MISSING_ARROW`, `UNKNOWN_HEADER`, `TOO_MANY_PARTICIPANTS`) allow pattern matching without the LLM reading natural language errors.

---

## 8. Token Budget by Response Mode

| Mode | Typical Output | Use When |
|:---|:---|:---|
| `summary` | `✓ Rendered sequence (8 events, 20 lines). Shown in terminal.` (~12 tokens) | Default — LLM doesn't need diagram content |
| `truncated` | First 20 lines + count of remaining (~80 tokens) | LLM needs to verify a few participants or steps |
| `full` | Complete rendered diagram (~200–2000 tokens) | LLM is doing code intelligence / node navigation |

---

## 9. Architecture: Zero LLM in the Hot Path

```
LLM generates Mermaid   →   validate_diagram (O(n) scan, 0ms)
                         →   render_diagram (pure Go, <5ms, no LLM)
                         →   Terminal output (direct to user)
                         →   Summary ACK to LLM (~10 tokens)
```

The LLM is involved **only** at the start (generating Mermaid source) and at the end (receiving the summary ACK). All parsing, layout computation, and Unicode rendering happen in a single statically-linked Go binary with sub-5ms cold start and **zero LLM API calls**.

This is the highest-accuracy, lowest-cost architecture for diagram generation:
- **No LLM hallucination in layout** — layout is deterministic geometry computation
- **No LLM round-trips for rendering** — renderer is pure Go
- **Structured errors** — LLM self-corrects in 1 shot, not 3
